# 曲库封面从哪来：三个来源、匹配规则、换目录会怎样

> 2026-11-24 排查记录 · 起因：审计「有多少首没封面」时口径错了一层，用户用截图纠正

---

## 一、结论

1. **曲库里的封面有三个来源**，代码按顺序试：对齐产物 → 磁盘缩略图 → 音频内嵌。
2. **对齐产物靠「路径哈希」和「同名兜底」两级匹配**；路径哈希在目录移动后必然失效，实际全靠同名兜底在工作。
3. 因此「换个目录还会不会显示」的答案是：**歌名不变、且 work 里同名目录只有一份 → 会；有同名曲目 → 可能不会**。
4. 872 首实测：内嵌 870 · 只有对齐封面 2 · 三个来源都没有 **0**。

---

## 二、三个来源与优先级

`internal/app/cover.go` 的 `thumbImage()` 依次尝试：

```
1. work/<歌名>_<10位哈希>/cover.jpg     对齐时抽出来的（要求 cover 不比音频旧）
2. work/covers/<16位哈希>.jpg            上次解码过的 128px 缩略图
3. 音频内嵌封面（FLAC PICTURE / MP3 APIC）
```

三者都没有 → 界面画渐变占位块（`artCover`），按歌名色相生成，不是图片。

**关键点**：第 1、2 层都是 `work/` 里的缓存，不跟着音频文件走；第 3 层在文件里，复制/移动都不丢。

## 三、对齐封面是怎么被找到的

### 写入侧（Python）

```python
# kiralrc/pipeline.py:66-67
key = hashlib.md5(str(audio_path.resolve()).encode()).hexdigest()[:10]
d = config.work_dir() / f"{audio_path.stem[:40]}_{key}"
```

目录名 = `歌名前 40 字` + `_` + `md5(音频绝对路径)[:10]`。

### 读取侧（Go）

```go
// internal/app/cover.go
resolved := EvalSymlinks + Abs(audioPath)
name := 文件名前 40 字
hash := md5(resolved)[:5]              // 10 个十六进制字符
path := index.byDir[fmt.Sprintf("%s_%x", name, hash[:5])]
if path == "" && len(index.byStem[name]) == 1 {   // 兜底：同名前缀只有一份
    path = index.byStem[name][0]
}
```

`indexCovers()` 的收录条件：目录名最后一个 `_` 之后正好 10 个字符、里面有 `cover.jpg` 且大于 512 字节。

### 实测（`E:\cloudy music`，872 首）

| 匹配方式 | 数量 |
|---|---|
| 路径哈希命中 | **0** |
| 同名兜底命中 | 51 |
| 没有对齐产物 | 821 |

路径哈希为 0，说明这批 work 目录**都是在旧路径下生成的**（用户挪过文件夹），现在完全依靠同名兜底。

举例（两首「疑似没封面」的曲目）：

```
张卫健、刘德华 - 高高在下
  目录名里的哈希  42b9ce492a    ← 旧路径算出来的
  当前路径算出来  f5995d22a6    ← 对不上
  实际匹配：byStem 只有一份 → 命中
```

## 四、换目录会怎样

| 情况 | 结果 |
|---|---|
| 歌名不变，work 里同名前缀目录只有一份 | **照旧显示**（与目录无关） |
| 换目录后重新对齐一次 | 新路径生成新目录，哈希直接命中，最稳 |
| 同一个「歌手 - 歌名」在 work 里有两份 | 兜底失效 → 退到内嵌；无内嵌则显示渐变占位 |
| 音频自带内嵌封面 | 不受影响 |
| 只改歌名（文件重命名） | 前 40 字变了，两级都失效 |

本库已有 **7 组同名 stem**（例如 `折戸伸治 - 凍土高原`、`折戸伸治 - 風を待った日`、`麻枝准 - 夢の跡`），这几组一旦各自都对齐过，兜底就会失效。

另有两点容易忽略：

- `work/covers` 的缩略图键是 `md5(路径 + 修改时间)[:8]` → **换目录后缓存失效**，会重新解一次图（重新解时会再走上面三级），不影响最终能否显示。
- 移动文件不改变修改时间，所以「cover 比音频新才用」这条检查不受目录迁移影响。

## 五、如果要改稳（未实施）

问题根源是**用绝对路径当缓存键**。三种改法，按推荐排序：

1. **改用音频自身特征**：`歌名_<文件大小>_<修改时间>` 或内容 md5 前 10 位。移动、改目录都不变，读写两侧改动最小。
2. **同名多份时确定性消歧**：按时长/大小挑最接近的那份，别直接放弃。
3. **兼容旧目录**：先试新键，再退回「路径哈希 → 同名唯一」两级，历史 `work/` 无需重建。

涉及文件：`kiralrc/pipeline.py`（生成）与 `internal/app/cover.go`（匹配），两边算哈希的规则必须完全一致。

## 六、附：这次排查顺手修掉的真 bug

审计时发现「我们只认出 560 首有内嵌封面，mutagen 说 870」——**ID3v2.3 的帧长不是 syncsafe**：

```
v2.2  帧头 6 字节：ID 3 字节 + 长度 3 字节（普通大端）
v2.3  帧头 10 字节：长度 4 字节（普通大端）     ← 原来按 syncsafe 读，错了
v2.4  帧头 10 字节：长度 4 字节（syncsafe）
```

v2.3 里只要前面出现过 >127 字节的帧（`USLT`、`TXXX` 基本都超），指针就串位，后面的 `APIC` 再也扫不到。修完 872 首里内嵌封面 560 → 870，与 mutagen 完全一致（提交 `2fb28f5`）。

**教训**：统计「有没有封面」必须按界面的完整口径（三个来源）来算，且看到「对齐产物 0」这种可疑值要先怀疑自己的取数环境（测试进程里 `appRootDir()` 指向临时目录，`work/` 根本扫不到）。
